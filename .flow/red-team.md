# Red-Team: Analysis Plan Studio 独立产品方案 v1.0

> 评审对象：`.flow/proposal.md`（本地优先、单场景、计划—确认—受限执行—证据验收的分析计划工具）
> 评审性质：策略红队——攻击承载性假设，非穷举风险清单。结论：**go**（无 kill 准则已被满足），但下列 5 条承载假设应在建软件之前或同时用最便宜的方式验证。

## Top Kill-Assumptions（按 影响 × 错误概率 × 验证便宜度 排序）

### KA1｜用户真的愿意"先确认计划再跑"，而不是直接让 Agent 写代码

- **Claim：** 分析人员会接受"编制计划 → 显式确认 → 受限执行"的前置流程，因为它把口径争议前移、减少返工；业务负责人愿意基于计划卡片做审查。
- **Steelman：** 被 Agent"换口径、删异常值、静默改样本"坑过的分析师，对可审阅的行为契约有真实痛感；不会审代码的负责人确实无法判断 Agent 是否守约，这是现有工具链的真空。
- **Fails if：** 真实任务里用户在看到确认界面/表单的摩擦后，多数选择绕过工具直接 prompting 或写 SQL——工具变成"演示时严谨、日常时闲置"的仪式性软件；或 14.3 的"计划理解偏差"指标显示前置确认根本没抓到过真实争议，只是增加了表单工作。
- **本周可取证据：** 不写代码，用共享文档 + 现有 coding agent 做 2—3 次"人工传译版计划确认"：分析前把口径、范围、退款规则、同店资格写成一张确认卡，让真实用户签字，观察（a）用户是否愿意填/签，（b）确认过程是否真的在执行前暴露了口径分歧。
- **Kill criterion：** 若 ≥2/3 的试用任务中用户拒绝完成前置确认，或确认卡从未暴露过任何真实分歧，价值假设不成立，应转向"事后验收器"（先跑再核）形态而非"事前计划"形态。
- **Cheapest test：** 一次真实周度销售复盘任务 + 一页纸确认卡，成本半天。

### KA2｜治理面（12 类对象/5 道门禁/9 个接口）相对单一场景是否过重，能否按时交付

- **Claim：** P0 能在可接受时间内交付完整闭环（契约+门禁+受限执行+证据+模板+5 页面），且"受限执行与证据验收不能删"。
- **Steelman：** 方案自己识别了"退化为 IR 编辑器"的风险并明确拒绝对冲（P0 必须带 Runner 与验收）；M0→M3 的依赖排序和"先机器闭环后界面"是正确的工程纪律。
- **Fails if：** 单人/小团队在 M0（契约+金标准+失败样例）和 M1（机器闭环）上耗费远超预期，导致数月内没有可用的端到端产物；或者为赶上交付悄悄砍掉门禁（门禁只剩 UI 标记），恰好违背方案核心承诺。治理面是为未来多场景预付的成本，若第二场景迟迟不来，这套 machinery 对一个 SQL group-by 场景就是过度建设。
- **本周可取证据：** 对 M0+M1 做 walking skeleton 时间盒估算（对象 Schema 起草、digest 规则、一个方法的执行回执），换算成工程师-日；对照可用人力得出 P0 真实日历预期。
- **Kill criterion：** 若 M0+M1 无法在约 2—4 周（单人全职当量）内跑通最小机器闭环，应砍治理面对象数量（如 Approval/EvidenceBundle/RunRecord 先合并为轻量记录）或推迟 UI（M2），而不是全面铺开。
- **Cheapest test：** 1—2 天时间盒内写出 schema 草案 + 一个方法的执行回执原型，测实际速度外推。

### KA3｜真实用户答得出（且愿意答）阻断性确认项

- **Claim：** 口径未确认即阻断（退款归属、比较范围、coverage manifest、同店资格清单）是正确设计，且这些信息在实践中可获得。
- **Steelman：** "把没有记录当零销售""把门店交集包装成同店"是真实的分析事故源；阻断比静默补齐诚实。方案也允许"全量观察范围"作为降级口径。
- **Fails if：** 真实零售数据里根本没有 coverage manifest，用户自己也不掌握退款归属规则——多数任务永久停在 NEEDS_INPUT，工具被判定"不可用"；或者团队为可用性悄悄放宽必需项，等价于门禁失守。
- **本周可取证据：** 取过去 3 次真实"销售为什么下降"分析，检查：字段是否齐、覆盖清单是否存在、口径问题当时由谁回答、答对了吗。
- **Kill criterion：** 若 <2/3 的历史任务能在合理追问下凑齐 G1 所需确认项，说明阻断项配置与目标用户的现实数据成熟度错配，需要重新分级"必需 vs 可披露限制后放行"。
- **Cheapest test：** 桌面研究 + 与数据 owner 一次 30 分钟访谈，零代码。

### KA4｜固定方法集真能覆盖该场景的真实变体

- **Claim：** 销售差异与多维贡献拆解可由版本锁定的固定方法集（质量检查/范围/整体差异/分组拆解/对账）完成。
- **Steelman：** 这是刻意收窄的、算术上可对账的场景，是所有分析场景中最接近"纯函数"的一个；选它做首期正是为了可验证。
- **Fails if：** 真实提问迅速滑向混合效应（价格×销量 mix）、流量×转化分解、新老店/开关店对照、节假日对齐——每项都"只差一个方法"但都在注册表之外，用户第一次碰壁就回到自由编码路径，"受限方法集"的核心卖点变成核心瓶颈。
- **本周可取证据：** 枚举过去 6—12 个月真实发生过的"销售下降归因"类分析实际用到的方法清单，标注哪些落在首期注册表内。
- **Kill criterion：** 若固定方法集只能回答 <70% 的该场景真实实例，要么把场景定义再收窄（并在模板适用边界里写明），要么在 P0 注册表内补齐高频方法，否则 T01"用模板完成全部首期流程"会在真实数据上失败。
- **Cheapest test：** 桌面研究：翻历史分析记录列方法清单，半天。

### KA5｜单人本机治理（digest/批准/快照）产生真实价值

- **Claim：** 版本化批准、内容指纹、快照复现在单用户本机形态下就有价值（自己复核、跨期复用、向负责人交代）。
- **Steelman：** 跨周期复用（T19）和"同数据复跑生成新 run_id"是具体、可演示的价值点；向第二类用户（负责人）出示证据链是真实场景。
- **Fails if：** 实践中从没有第二双眼睛看这些记录，跨期复用也被"改个日期重跑"替代，digest 体系沦为自我确认的成本——此时应把治理投入转移到"结果可信度"（对账、覆盖检查）而非"过程审批"。
- **本周可取证据：** 在 KA1 的纸质确认卡试验中，观察负责人是否真的阅读计划卡/证据，还是只看结论页。
- **Kill criterion：** 若 3 次真实任务中负责人均只看结论，P1/P2 前不再加码审批类功能，把预算集中在验收检查器。
- **Cheapest test：** 并入 KA1 试验，零额外成本。

## What's Well-Reasoned（站得住的部分）

- **认识论纪律罕见地好：** 全文反复区分"规范合法 ≠ 分析正确"、"提示词要求 ≠ 执行约束"、"外部 Agent 自评 ≠ 证据"，每处能力声明都标注了验证边界。这比多数同类方案诚实一个量级。
- **验收矩阵是真实可执行的：** T01—T24 覆盖了失败路径、防伪回执、越界注入、无网运行，且明确了"成功/失败/受限三类样例都要交付"，直接可转为测试用例。
- **范围控制明确：** 单场景、五页面、固定方法集、明确的后置清单（P1/P2）、"不是第二个 Xanthil"的边界反复强化，膨胀风险有制度性防御。
- **工程排序正确：** 契约与样例先行（M0）→ 机器闭环（M1）→ 界面（M2）→ 失败路径（M3），避免了"先做 UI 后补治理"的常见死法。
- **安全姿态务实：** 不声称子进程即沙箱、DuckDB 限制有官方依据、回环绑定+会话令牌、压缩包按不可信输入处理——没有一处靠名词充安全。

## What I Couldn't Assess

- **现有代码复用面：** 方案自述"未审查现有仓库"，Analysis Core / DAME / Semantic Context Runtime 中已有 IR/验证/执行实现的可复用量未知，直接影响 KA2 的工期判断。
- **人力与日历：** 文档明确 M0—M3 只是依赖序而非时间承诺，但没有任何容量信息，无法判断 P0 的真实交付窗口。
- **平台侧需求的真实性：** Xanthil/JuanerAI 集成（P2）是否有真实的平台侧需求方，超出本文档可判定范围。
- **数据现实：** 试用方真实零售数据的成熟度（字段完整性、覆盖清单、门店主数据）未知，直接决定 KA3。

## 结论

**Verdict: go。** 方案在认识论、验收设计、范围控制上是同类中少见的高质量基线；没有 kill 准则已被满足。但 KA1（用户愿意前置确认）是整个产品的心脏假设，且验证成本极低（半天纸质试验）——应在写第一行 Schema 之前或与 M0 并行完成；KA2（工期现实性）在 M0 第一周内即可自校准。
